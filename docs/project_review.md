# 项目复盘与改进记录

## 已完成的优化点

| 维度 | 原问题 | 改进方案 | 设计思路 |
|---|---|---|---|
| 指标口径 | 月报只有 GMV/AOV，无法完整回答增长来自哪里 | 新增 `orders_per_user`、环比及 GMV 三因子恒等式 | 不把三因子的乘法关系误说成因果归因 |
| 数据质量 | 只检查空主键/重复，缺少业务时间和关联检查 | 新增质量门禁 SQL 与 Python 输出 | 先看失败行，再决定是否发布指标 |
| SQL 一致性 | SQL RFM 用系统当前日期，Python 用数据截止日 | SQL 改为数据最大日期+1 | 同一口径跨工具可复现 |
| 留存 | 尾部 cohort 可能尚未成熟 | 输出观察月数和 M3 成熟标记 | 不横比未成熟 cohort |
| 统计 | 二元转化用 t 检验且无精度说明 | 改为比例差 z 检验，输出 CI 和近似 MDE | 不显著不等于没有效果 |
| 收益测算 | 可能被误读为年化收益或预测 | 标为观察窗情景值，写明公式/成本缺失 | 这是待验证的 GMV 情景，不是 ROI |
| 展示 | README 未能快速传达价值 | 增加项目概述和验收清单 | 先讲价值，再讲技术细节 |

## 拿到真实业务数据后需补充

1. 记录下载日期、数据版本、行数和哈希，避免数据漂移。
2. 执行质量门禁并解释异常；对缺失评价报告覆盖率。
3. 将策略情景替换成真实基线、毛利、触达成本和预先定义的实验设计。
4. 在仪表盘中增加数据截止日、数据模式（模拟/真实）和口径提示。

## 值得深入讨论的问题

- 为什么 GMV 不用 `payment_value`？答：这里定义为商品价加运费的下单商品口径；支付表可能有分次支付，支付方式仅按最大支付金额分类。若讨论实收，应另建支付口径并对账。
- 交付逾期导致差评吗？答：当前只能观察相关性；需要控制品类、地区和价格，或以履约实验/准实验识别因果。
- RFM 为什么可信？答：它是可解释的规则分层，不是因果模型；量化阈值和观察窗会影响分层，真实上线前需要回测复购与利润。
